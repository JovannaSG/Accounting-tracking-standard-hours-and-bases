# Руководство администратора и пользователя

Система «Учёт нормочасов» — веб-приложение (Streamlit) для нормированного
учёта трудозатрат аутсорсинговых бухгалтеров. Данные выгружаются из
продуктивных баз 1С:Бухгалтерия через OData-сервис 1С:Фреш, операции
оцениваются по нормам, результат показывается в отчёте и выгружается в Excel.

Основные понятия:

- **База 1С:Фреш (клиент)** — одна продуктивная база, соответствует одному
  клиенту аутсорсера. Для каждой базы создаётся запись во вкладке «Базы и
  доступ» с реквизитами OData-пользователя.
- **Норма** — трудозатраты на одну операцию вида документа (в минутах) плюс
  коэффициент сложности. Нормочасы = операций × минут/60 × коэффициент.
- **Сотрудник** — бухгалтер аутсорсера. Записывается по полному ФИО; у него
  может быть алиас (техническое имя пользователя в 1С вида `Е_Кирищёнок`).
- **Пользователь системы** — учётная запись для входа в приложение.
  Бухгалтеру привязывается сотрудник, управляющий или администратор — нет.

---

## 1. Роли и права доступа

Права задаются ролью пользователя (поле «Роль» в учётной записи):

| Раздел приложения | Администратор | Руководитель | Бухгалтер |
|---|---|---|---|
| Отчёт (формирование, Excel) | полностью | полностью | только свои операции |
| Диагностика OData | да | да | да |
| Нормы трудозатрат | редактирование | редактирование | нет |
| Сотрудники | редактирование | редактирование | нет |
| Базы и доступ | редактирование | просмотр | просмотр |
| Пользователи | редактирование | нет | нет |

Пояснения:

- **Администратор** видит все базы и все операции, управляет учётными
  записями, базами, нормами и сотрудниками.
- **Руководитель** видит все базы, все операции и отчёты; правит нормы и
  сотрудников; учётные записи и базы — только просмотр.
- **Бухгалтер** видит только **свои** операции (по сотруднику, привязанному к
  его учётной записи) и только те базы, которые указаны у него в «Доступных
  базах». Блок «Не распределены» бухгалтеру не показывается.

Вкладки, недоступные роли, не отображаются в меню приложения.

## 2. Установка и запуск

### 2.1 Локально (разработка)

```bash
python -m venv .venv
# Windows: .venv\Scripts\activate | Linux/macOS: source .venv/bin/activate
pip install -r requirements.txt
python app/run.py
```

Открыть в браузере: **http://127.0.0.1:8503** (порт задаётся переменной
`UI_PORT`).

### 2.2 Docker (production)

Приложение **не запустится без `users.json`** — это намеренно: иначе порт,
доступный по сети, остался бы без аутентификации. Первый запуск состоит из
трёх шагов, порядок обязателен:

```bash
# 1. Получить пароль администратора (выполняется в корне проекта, на хосте)
python -m core.auth hash "пароль_администратора"

# 2. Поднять контейнер: он завершится с ошибкой — это ожидаемо
docker compose up -d --build

# 3. Положить users.json в том и запустить
docker cp users.json norm-hours:/data/users.json
docker compose start norm-hours
```

`docker cp` работает и с остановленным контейнером, поэтому шаг 2 нужен
лишь для того, чтобы контейнер и том существовали. Сообщение об ошибке
подсказывает недостающие шаги:

```
ОШИБКА: не найден файл пользователей: /data/users.json
```

Проверить состояние: `docker compose ps` — ожидается `Up (healthy)`;
`docker compose logs -f` — журнал.

Открыть в браузере: **http://<хост>:8503** (левую часть проброса можно
поменять в `docker-compose.yml`, например `"8504:8503"`).

Если на одной виртуальной машине несколько экземпляров приложения, у каждого
должны быть свои: внешний порт, имя контейнера (`container_name`) и том.
Правьте эти три значения в копии `docker-compose.yml`:

| Значение | Основной | Второй экземпляр |
|---|---|---|
| `ports` | `"8503:8503"` | `"8504:8503"` |
| `container_name` | `norm-hours` | `norm-hours-2` |
| `volumes.norm-hours-data.name` | `norm-hours-data` | `norm-hours-data-2` |

Ключ `-p` проекта в `docker compose -p <имя>` **не** переименовывает том и
контейнер, если имя задано явно: эти значения правятся вручную, как в таблице
выше.

Рабочие данные живут в docker-томе `norm-hours-data` (смонтирован в `/data`):

- `/data/norm_hours.db` — SQLite-БД приложения (пользователи, базы, нормы,
  сотрудники);
- `/data/users.json` — конфиг пользователей; он **не** создаётся
  автоматически, положите его в том командой из раздела 3.1.

Полезные команды:

```bash
docker compose logs -f          # журнал
docker compose restart          # перезапуск
docker compose down             # остановка (данные в томе сохраняются)
```

Контейнер перезапускается до трёх раз (`restart: on-failure:3`): при
отсутствующем `users.json` он останется остановленным, чтобы не создавать
цикл перезапусков, засоряющий журнал.

**Бэкап** данных — это копия тома `norm-hours-data`. Остановите контейнер,
затем:

```bash
docker compose stop
docker run --rm -v norm-hours-data:/data -v %cd%:/backup \
  alpine tar czf /backup/norm-hours-data.tar.gz -C /data .
docker compose up -d
```

(В PowerShell вместо `%cd%` используйте `${PWD}`.)

Чтобы обновить `users.json` внутри тома без остановки контейнера:

```bash
docker cp users.json norm-hours:/data/users.json
docker compose restart norm-hours
```

### 2.3 Переменные окружения

| Переменная | Назначение | По умолчанию |
|---|---|---|
| `AUDIT_DB_PATH` | путь к SQLite-БД приложения | `norm_hours.db` |
| `AUDIT_USERS_CONFIG` | путь к конфигу пользователей `users.json` | `users.json` |
| `AUDIT_USERS` | fallback-пользователи `логин:хэш,логин2:хэш2` (PBKDF2) | пусто (выкл.) |
| `UI_HOST` | адрес для Streamlit | `127.0.0.1` |
| `UI_PORT` | порт Streamlit | `8503` |

## 3. Настройка для администратора

### 3.1 Первый запуск и создание учётных записей

Аутентификация включается автоматически, когда в системе появляется хотя бы
одна учётная запись. Первая запись создаётся из файла `users.json`
(seed-механизм работает только когда таблица пользователей пуста).

1. Скопируйте шаблон и укажите пароль администратора:

   ```bash
   cp users.example.json users.json      # локально
   # в Docker: правьте users.json на хосте и переносите docker cp
   #   (см. 2.2, шаг 3)
   ```

   Формат файла:

   ```json
   {
     "admin": {
       "role": "admin",
       "password": "200000$<соль-hex>$<дайджест-hex>"
     },
     "buhgalter": {
       "role": "accountant",
       "allowed_urls": ["https://msk1.1cfresh.com/a/ea/1119958"]
     }
   }
   ```

   Значение `password` — это PBKDF2-хэш, а **не пароль в открытом виде**
   (открытый текст при входе не принимается). Сгенерировать:

   ```bash
   python -m core.auth hash <пароль>
   ```

   Плейсхолдер `ЗАМЕНИТЕ_НА_ХЭШ_из_python_-m_core.auth_hash` из шаблона
   намеренно **не** создаёт учётную запись: в журнале появится сообщение
   `[users.json] пропущен 'admin' ...`, и вход будет невозможен. Такой
   заглушкой нельзя случайно оставить систему с паролем по умолчанию.

   Seed выполняется **один раз**, только когда таблица пользователей пуста.
   После первого запуска пользователи живут в БД (вкладка «Пользователи»),
   и правка файла `users.json` на них не влияет — управляйте ими в интерфейсе.
   Как принудительно переприменить файл, см. FAQ в конце руководства.

2. Запустите приложение и войдите под `admin`.
3. Первым делом смените пароль администратора: вкладка **«Пользователи»** →
   выберите себя → «Новый пароль» → «Сохранить».
4. Остальные пользователи создаются там же во вкладке «Пользователи» (см. 3.2).

Учётную запись можно задать и через переменную `AUDIT_USERS`
(`логин:хэш,логин2:хэш2`) — она действует как fallback, если записи нет в БД.

**Защита входа.** После 5 неудачных попыток входа логин блокируется на
5 минут (счётчик попыток в памяти процесса — после перезапуска контейнера
обнуляется). Пароль, задаваемый в интерфейсе, должен быть не короче
8 символов. Сессия завершается автоматически, если пользователь не нажимал
ничего 30 минут; таймаут настраивается переменной `UI_IDLE_TIMEOUT_MIN`
(`0` — не завершать).

### 3.2 Вкладка «Пользователи» (только администратор)

Добавление:

- **Логин** — имя для входа (сравнение регистронезависимое);
- **Роль** — Администратор / Руководитель / Бухгалтер;
- **Пароль** (дважды, не короче 8 символов; флажок «Показать пароль»
  открывает оба поля);
- **Доступные базы** — URL баз 1С:Фреш, по одному на строку. Поле влияет
  только на бухгалтера: он видит строго эти базы. У руководителя оно
  информативное — руководитель видит все базы;
- **Сотрудник** — привязка бухгалтера к сотруднику (его операции и только их
  он видит в отчёте; привязка видна только для роли «Бухгалтер»).

Над формами выводится таблица всех пользователей: логин, роль (русскими
словами), признак активности, привязанный сотрудник и список доступных баз.

Редактирование: выбор пользователя → форма с ролью, активностью, сменой
пароля, списком баз и привязкой сотрудника. Пустой пароль означает
«оставить прежний».

Удаление: выбор пользователя из списка → подтвердить флажком.

Защита: нельзя разжаловать или удалить **последнего** действующего
администратора; нельзя удалить собственную учётную запись.

### 3.3 Вкладка «Базы и доступ»

Добавьте по одной записи на каждую базу 1С:Фреш (один клиент = одна база):

- **Название** — клиент;
- **URL OData** — адрес публикации, например
  `https://msk1.1cfresh.com/a/ea/1119958`;
- **Логин/пароль** — OData-пользователя базы (роль
  «УдаленныйДоступOData» в 1С:Фреш);
- **СНО** — система налогообложения клиента (заполняется вручную);
- **Группа** — необязательная группировка клиентов;
- **Виды документов этой базы** — список ключей из реестра `doc_types.json`,
  которые выгружаются по этой базе. Пустой список (по умолчанию) означает
  «выгружать все виды». Список действует как **белый список**: он сужает
  выгрузку, а блок операций в отчёте выбирает уже внутри него. Это удобно,
  если конкретная база не публикует часть сущностей — вкладка
  «Диагностика OData» покажет, какие именно.

Пароли клиентских баз можно зашифровать. Сгенерируйте ключ и задайте
переменную окружения `AUDIT_DB_SECRET_KEY`:

```bash
python -c "import base64,secrets; print(base64.urlsafe_b64encode(secrets.token_bytes(32)).decode())"
```

После этого новые и изменённые пароли сохраняются в шифрованном виде
(префикс `enc:v1:`), а ранее сохранённые открытыми — читаются как есть и
перешифровываются при первом изменении. **Храните ключ отдельно от БД**:
при его утере пароли баз восстановить нельзя, их придётся ввести заново.
Если ключ не задан, поведение прежнее — пароли лежат в открытом виде.

Если ключ **задан, но неверен** (опечатка, ключ от другой базы), приложение
не отключает шифрование молча: импорт и правка баз останавливаются с
пояснением, а пароль в открытом виде не записывается. Ранее эта ошибка была
тихой — база сохранялась с незашифрованным паролем, а при чтении чужого
ключа подставлялся пустой пароль. СНО, группу и виды документов при этом
по-прежнему можно исправить: токен пароля не перетирается.

#### Массовый импорт из файла

Если баз много, добавлять их по одной не нужно. В той же вкладке
«Базы и доступ» есть блок «Массовый импорт из файла»:

1. Нажмите «Файл с клиентскими базами» и выберите `client_databases.json`
   (или CSV со столбцами «название, ссылка, логин, пароль»; подходят и
   английские заголовки `name, url, login, password`).
2. Проверьте сводку: сколько баз готово к импорту, сколько уже есть,
   сколько записей без ссылки. При желании откройте предпросмотр первых
   записей.
3. Нажмите «Импортировать N баз».

Что важно знать:

- **Существующие базы не перезаписываются.** Совпадение определяется по
  адресу, поэтому повторная загрузка того же файла ничего не меняет и
  дублей не создаёт. Права доступа и СНО у таких баз остаются прежними.
- **Записи без адреса пропускаются** и показываются в отчёте — их нужно
  заполнить вручную.
- **Названия сохраняются как в файле**, включая префиксы вида `1;`,
  `2;`: они попадают в список баз и в отчёт, поэтому по названию видно,
  к какой группе относится клиент.
- Пароли шифруются, если задан `AUDIT_DB_SECRET_KEY`.
- Секреты остаются на вашем компьютере: файл читается в момент импорта и
  никуда не отправляется. Сам `client_databases.json` добавлен в `.gitignore`
  и в репозиторий не попадает; для примера формата рядом лежит
  `client_databases.example.json` без паролей.

Формат записи:

```json
{ "name": "1;ООО Пример", "url": "https://msk1.1cfresh.com/a/ea/1119958",
  "login": "odata.user", "password": "..." }
```

СНО, группа и виды документов в файле не переносятся — их удобнее
заполнить после импорта: у всех новых баз они пустые, а пустой список
видов документов означает «выгружать все».

Администратор и руководитель видят все базы; бухгалтер — только указанные у
него в «Доступных базах». Для manager/accountant вкладка работает в режиме
просмотра.

### 3.4 Вкладка «Нормы»

- Кнопка **«Засеять нормы по умолчанию»** добавляет нормы по всем видам
  документов из реестра (для новых действий не затирает уже существующие
  нормы).
- Редактирование: выберите вид документа из списка (название + ключ) и
  измените норму в минутах, коэффициент сложности, СНО, комментарий или
  признак «Норма активна». Выключенная норма не участвует в расчёте.
- **Новый вид документа** (форма внизу вкладки) — для документа, которого
  нет в реестре: задайте ключ (`doc_type`, латиницей, уникально),
  наименование для отчёта, категорию, OData-сущность, единицу измерения,
  норму в минутах и коэффициент. После создания вид сразу появляется в
  списке редактирования и исчезает из предупреждения об отсутствии норм.

  Ключ из реестра менять не нужно — правка существующей записи описана
  выше. Реестр `doc_types.json` по-прежнему нужен, чтобы приложение
  *выгружало* этот документ из 1С: без записи в реестре норма есть, а
  данных не будет.
- **Виды документов в реестре** добавляются правкой `doc_types.json`
  (ключ, категория, наименование, OData-сущность, единица измерения).

### 3.5 Вкладка «Сотрудники»

- **ФИО** — как минимум это имя должно полностью совпадать с именем
  автора документа в 1С (иначе автор попадёт в «Не распределено»);
- **Пользователь 1С (алиас, опц.)** — техническое имя вида `Е_Кирищёнок`;
- **Роль сотрудника**, **Фонд часов в месяц** (по умолчанию 130) — для отчёта
  «Загрузка сотрудников»;
- **Массовый импорт по ФИО** — вставьте список имён по одному на строку;
  повторный импорт того же списка не создаёт дублей (ФИО — ключ записи);
- Удаление — через выбор в списке.

Учётные записи для импортированных сотрудников при этом **не создаются**:
вкладка «Пользователи» остаётся отдельной сущностью, а сотрудник
привязывается к учётной записи через поле «Содрудник» (в БД —
`users.employee_full_name`). Это сделано намеренно: список сотрудников
ведёт кадровик, а логины и пароли — администратор.

Вкладка разделена на четыре блока:

- **Новый сотрудник** — добавление записи;
- **Редактирование** — выбор сотрудника из списка и правка его полей.
  Запись адресуется по внутреннему `id`, поэтому **ФИО можно менять**:
  это обычная правка, а не создание нового сотрудника. При переименовании
  автоматически обновляется привязка учётных записей бухгалтеров
  (вкладка «Пользователи» → «Сотрудник»), поэтому их отчёт не станет
  пустым. Если такое ФИО уже занято другим сотрудником, система отклонит
  правку и покажет ошибку — ФИО должны быть уникальны.
  При желании выключите сотрудника флажком «Сотрудник активен»;
- **Массовый импорт по ФИО** — создание сотрудников по списку имён;
- **Удаление** — выбор сотрудника и подтверждение.

## 4. Работа пользователя

### 4.1 Сайдбар (общие элементы)

- **База 1С:Фреш** — выбор клиентской базы (список зависит от роли);
- **Период** — месяц / квартал / год / произвольные даты;
- **Блок операций** — категории документов: ровно три — «Банк и касса»,
  «Первичные документы», «ТМЦ и ОС»;
- **Вариант отчёта** — готовые наборы группировок (ТЗ §9.3): по клиенту,
  по сотруднику, по видам документов, по клиентам за месяц, по видам
  операций, «Операции без ответственного». Вариант «Пользовательская»
  оставляет выбор группировок вручную. Смена варианта не требует повторной
  выгрузки из 1С — используется уже загруженный кэш;
- **Группировка** — по клиенту, сотруднику, виду документа и операции;
- кнопка **«Сформировать отчёт»**;
- после формирования — элементы отборов и **сортировка**. Кнопки
  «Скачать Excel» и «Очистить отчёт» находятся не в сайдбаре, а под
  таблицами отчёта (см. 4.2).

Если базы не настроены, в сайдбаре предлагается ввести URL/логин/пароль
OData однократно («без сохранения») для разовой проверки.

Под таблицей отчёта в сайдбаре появляется строка **«Применяются отборы:
…»** — она перечисляет активные фильтры, чтобы не забыть о них.

**Сортировка** (ТЗ §9.2) по умолчанию: клиент ↑, вид документа ↑,
количество операций ↓, трудозатраты ↓. Сортировку можно изменить в
сайдбаре (колонка и направление); она действует только на экран — в Excel
выгружается сортировка по умолчанию, чтобы подытоги по клиентам не
разрывались.

### 4.2 Вкладка «Отчёт»

1. Выберите базу, период, блоки и группировку; нажмите «Сформировать отчёт».
   Данные выгружаются из 1С:Фреш за период и кэшируются в текущей сессии.
   Если у базы в «Базах и доступ» задан список видов документов, выгрузка
   идёт только по нему.
2. После формирования появляются итоги (операций, нормочасов) и таблица
   отчёта. Если сменить базу или период, кэш сбрасывается автоматически.
3. **Предупреждение о нормах.** Если по каким-то видам документов норма
   не задана, над таблицей выводится жёлтый блок со списком этих видов —
   они посчитаны с нормой 0. Документы из этого списка **не искажают**
   итог, но их трудозатраты не учтены. Администратор закрывает пробел во
   вкладке «Нормы» (форма «Новый вид документа»). Бухгалтеру это
   предупреждение не показывается.
4. Под таблицей — фильтры по колонкам отчёта (после формирования) и блок
   **«Загрузка сотрудников»** (операции, часы и доля от фонда по каждому
   сотруднику).
5. Блок **«Не распределены»** — авторы, для которых нет сотрудника с таким
   ФИО/алиасом. Администратор должен добавить их во вкладку «Сотрудники».
   Бухгалтерам блок не показывается.
6. У варианта «Отклонение от нормы» выводится предупреждение: учёт
   фактического времени не подключён (очередь II), сравнение нормы и факта
   пока недоступно.
7. Под данными — панель действий:
   - **«Скачать Excel (.xlsx)»**;
   - **«Очистить отчёт»** — сбрасывает кэш и возвращает вкладку в
     исходное состояние. Фильтры, база и период в сайдбаре сохраняются,
     кэш выгрузки из 1С удаляется, чтобы отчёт можно было сформировать
     заново (например, с другими блоками операций). Кнопка нужна в том
     числе потому, что смена блоков операций сама по себе не сбрасывает
     уже выгруженные данные.
   Обе кнопки находятся в теле вкладки, под таблицами; сайдбар содержит
   только ввод и отборы.

### 4.3 Выгрузка в Excel

Кнопка **«Скачать Excel (.xlsx)»** в панели действий под таблицами отчёта
формирует файл из трёх листов:

1. **Отчёт** — данные как на экране: итоги по каждому клиенту и общий итог;
2. **Загрузка сотрудников** — часы и доля загрузки по сотрудникам;
3. **Сводка по клиентам** — клиент, ИНН, количество операций, нормочасы,
   доля от общего итога (%).

Если часть видов документов не удалось выгрузить (например, сущность не
опубликована), это показывается в отчёте отдельным блоком
«Виды документов, которые не удалось загрузить» (бухгалтеру не виден).

Имя файла: `normirovanie_<период>.xlsx`.

### 4.4 Вкладка «Диагностика OData»

Кнопка **«Проверить состав публикации»** читает `$metadata` выбранной базы и
показывает, какие сущности видов документов опубликованы (Да/НЕТ). Если
документ не выгружается — в первую очередь смотрите сюда, затем во вкладку
«Нормы» (ключи видов документов).

## 5. Частые вопросы

**Форма входа не появляется.** В системе нет ни одной учётной записи —
аутентификация отключена. Создайте первую запись в `users.json` (см. 3.1)
и перезапустите приложение.

**Забыт пароль администратора.** Остановите приложение и очистите таблицу
пользователей, затем перезапустите — приложение создаст записи заново из
`users.json`:

```bash
# локально
python -c "from core import db; db.init_db(); import sqlite3, os; p=db._DB_PATH; c=sqlite3.connect(p); c.execute('DELETE FROM users'); c.commit(); c.close()"
# Docker
docker compose exec norm-hours python -c "from core import db; import sqlite3; c=sqlite3.connect(db._DB_PATH); c.execute('DELETE FROM users'); c.commit(); c.close()"
```

После чего задайте новый пароль в `users.json` и перезапустите.

**«Порт занят».** Приложение уже запущено (проверка в `app/run.py`).
Остановите старый экземпляр и повторите запуск.

**Документы не выгружаются.** Проверьте «Диагностика OData»: сущность может
не публиковаться в составе. Отдельно проверьте, что у OData-пользователя базы
есть роль «УдаленныйДоступOData».

**Операции «не распределены».** Добавьте сотрудника с ФИО, совпадающим с
именем автора в 1С (или укажите алиас `user_1c`) во вкладке «Сотрудники».

**В отчёте жёлтое предупреждение о нормах.** В базе есть документы, для
которых в реестре норм нет ни записи, ни значения (0). Они посчитаны с
нулевой нормой и в итог не вошли. Список видов — в самом предупреждении.
Закройте пробел во вкладке «Нормы» → «Новый вид документа»: укажите ключ,
наименование и норму в минутах. Если вид уже есть в реестре, но норма
пустая — откройте его в списке редактирования и задайте значение.

**Не удаётся переименовать сотрудника.** ФИО уникальны: система отклонила
правку, потому что такое ФИО уже занято. Выберите другое имя либо сначала
переименуйте второго сотрудника.

**После переименования сотрудника бухгалтер видит пустой отчёт.**
Такого быть не должно: привязка учётной записи обновляется автоматически.
Проверьте, что ФИО в «Пользователи» → «Сотрудник» совпадает с ФИО во
вкладке «Сотрудники», и что сотрудник активен (не выключен флажком
«Сотрудник активен»).

**«Не удалось прочитать пароли клиентских баз» / импорт остановлен.**
Ключ `AUDIT_DB_SECRET_KEY` задан, но неверен: в нём опечатка либо он от
другой базы. Приложение специально останавливает импорт и правку баз, чтобы
пароль не записался в открытом виде. Пересоздайте ключ (команда в 3.3),
задайте его в окружении и перезапустите приложение. Если в базе уже есть
пароли, зашифрованные прежним ключом, их придётся ввести заново — либо
восстановить прежний ключ.

**Импорт из файла ничего не добавил.** Сравните сводку перед импортом:
если «Готово к импорту: 0», все базы из файла уже есть в базе (совпадение по
адресу) — это ожидаемое поведение, а не ошибка. Записи без адреса
перечислены отдельной строкой и требуют ручного заполнения. Если в
сводке было «Готово к импорту: N», а после нажатия добавлено меньше —
посмотрите список ошибок под кнопкой.

**Смена блока операций ничего не меняет в отчёте.** Выгрузка из 1С
кэшируется в сессии, и повторный запрос делается только по кнопке
«Сформировать отчёт». Нажмите **«Очистить отчёт»** (под таблицей) и
сформируйте заново — либо сформируйте отчёт заново без очистки, если нужно
просто пересобрать итоги по уже загруженным данным.

**По клиенту выгружается меньше документов, чем ожидалось.** Проверьте
в «Базах и доступ» список «Виды документов этой базы»: он работает как
белый список. Пустой список означает «выгружать все».

**Бухгалтер не видит свои операции.** Убедитесь, что в его учётной записи
выбрана роль «Бухгалтер», привязан сотрудник и в «Доступных базах» указаны
нужные URL.

**У бухгалтера пустой список баз.** В «Доступных базах» его учётной записи
перечислены URL баз; они должны совпадать с полем `url` записей во вкладке
«Базы и доступ».

**Вход заблокирован после нескольких неудачных попыток.** Сработала защита
от перебора: 5 попыток → блокировка на 5 минут. Подождите (или перезапустите
контейнер — счётчик попыток хранится в памяти процесса).

**Пароль от базы не подставляется после включения `AUDIT_DB_SECRET_KEY`.**
Значит, база была сохранена с другим ключом (или ключ утерян). Внесите
пароль заново во вкладке «Базы и доступ» — он сразу сохранится с текущим
ключом.

**Сессия завершилась сама.** Истёк таймаут бездействия
(`UI_IDLE_TIMEOUT_MIN`, по умолчанию 30 минут). Войдите заново; чтобы
отключить, задайте `0`.

**Контейнер сразу перезапускается и в журнале «не найден файл
пользователей».** Так и задумано: без `users.json` приложение не стартует
(иначе порт был бы доступен без аутентификации). Повторите шаги 2.2: сгенерируйте
хэш, `docker compose up -d`, `docker cp users.json norm-hours:/data/users.json`,
`docker compose start`. Политика `on-failure:3` остановит контейнер после трёх
попыток — журнал перестанет засоряться.

**В `users.json` лежит готовый шаблон, а вход не работает.** Обязательный
шаблон `ЗАМЕНИТЕ_НА_ХЭШ_из_python_-m_core.auth_hash` не является хэшем, поэтому
запись пропускается, а в журнале печатается
`[users.json] пропущен 'admin': ожидается хэш вида <итерации>$<соль>$<дайджест>`.
Замените значение на результат `python -m core.auth hash <пароль>`.

**Я исправил `users.json`, но пароль не изменился.** Seed выполняется **только
на пустой таблице пользователей**. Если запись уже создана, новый файл
игнорируется. Пользователей после первого запуска меняйте во вкладке
«Пользователи». Полный сброс (удалит всех пользователей приложения, базы,
нормы и сотрудники останутся):

```bash
docker compose exec norm-hours python -c \
  "import sqlite3;c=sqlite3.connect('/data/norm_hours.db');c.execute('DELETE FROM users');c.commit()"
docker cp users.json norm-hours:/data/users.json
docker compose restart norm-hours
```

Если контейнер остановлен, `docker cp` всё равно сработает, а вместо
`exec`/`restart` используйте `docker compose start`.

**Правлю JSON, а приложение ведёт себя как будто файла нет.** Проверьте
кодировку: «Блокнот» Windows, PowerShell 5.1 и VS Code могут сохранить файл
с меткой BOM в начале. Приложение это переживает (файлы читаются как
`utf-8-sig`), а вот сторонние скрипты, которые читают конфиг обычным
`utf-8`, — нет. В VS Code снимите галочку «Save with encoding: utf-8 with
BOM», в PowerShell используйте `[System.IO.File]::WriteAllText($p, $s, (New-Object
System.Text.UTF8Encoding $false))`.

**Бэкап: `tar` не находит каталог `./data`.** На хосте такого каталога нет —
данные лежат в томе `norm-hours-data`. Копируйте том командой из раздела
2.2, а не хостовый путь.

## 6. Структура данных

- `users` (БД): login, роль, хэш пароля (PBKDF2-HMAC-SHA256), список URL баз,
  флаг активности, привязка к сотруднику (ФИО). Привязка хранится текстом,
  поэтому при переименовании сотрудника она обновляется каскадно.
- `bases`: клиентская база (название, URL, логин/пароль OData, СНО, группа,
  список видов документов). Пароль шифруется Fernet, если задан
  `AUDIT_DB_SECRET_KEY` (префикс `enc:v1:`), иначе хранится как есть.
- `norms`: норма на операцию (doc_type, категория, минуты/часы, коэффициент,
  СНО, комментарий, флаг активности).
- `employees`: сотрудник (внутренний `id` + ФИО — уникальный ключ, алиас
  `user_1c`, роль, фонд часов, флаг активности). ФИО изменяемо: правка идёт
  по `id`, уникальность сохраняется.
- Пароли пользователей в открытом виде нигде не хранятся, только
  PBKDF2-хэши.
